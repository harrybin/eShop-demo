# ADR-002: Ordering DbContext pooling is enabled after constructor simplification

## Status
Accepted

## Date
2026-04-02

## Context
Ordering previously carried a DbContext construction pattern that prevented pooling from being safely enabled. The current state removes that blocker: `OrderingContext` now uses a `DbContextOptions<OrderingContext>` constructor, resolves `IMediator` via EF Core service provider in `SaveEntitiesAsync`, and `Ordering.API` registers `OrderingContext` using `AddDbContextPool<OrderingContext>`.

## Decision
Use DbContext pooling for Ordering (`AddDbContextPool<OrderingContext>`) and keep `OrderingContext` compatible with pooled activation.

## Consequences
- Pros: Better allocation and throughput characteristics under load from pooled context reuse.
- Pros: Registration is now aligned with intended performance guidance for high-throughput APIs.
- Cons: Future constructor changes in `OrderingContext` can silently break pooling compatibility if not reviewed.
- Cons: Feature additions that require scoped services in constructors must use supported patterns (for example EF internal service provider access) instead of extra constructor parameters.

## Alternatives considered
- Keep pooling disabled permanently: rejected due to avoidable performance cost.
- Use non-pooled `AddDbContext`: rejected for normal runtime path, acceptable only as a temporary fallback.
- Switch to `IDbContextFactory<OrderingContext>` everywhere: deferred; more invasive than needed for current design.
