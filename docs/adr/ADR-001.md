# ADR-001: Basket API is gRPC-first (no REST parity)

## Status
Accepted

## Date
2026-04-02

## Context
The Basket service is implemented as a gRPC endpoint (`AddGrpc`, `MapGrpcService<BasketService>`) and does not expose REST route groups today. The service contract is defined in `Proto/basket.proto`, and internal consumers are aligned to that contract.

## Decision
Keep Basket API gRPC-first and do not add REST parity endpoints in the current architecture wave.

## Consequences
- Pros: Single contract surface, strong typing from proto, and reduced duplicate endpoint maintenance.
- Pros: Lower drift risk between two API styles for the same basket operations.
- Cons: REST-native clients need a gateway/adapter or separate facade if direct HTTP/JSON access is required.
- Cons: Team conventions for minimal REST APIs are not directly reused in Basket.

## Alternatives considered
- Add full REST parity for all Basket operations: rejected for now due to duplication and contract drift risk.
- Replace gRPC with REST only: rejected because existing service contracts and consumers are already gRPC-based.
- Add selective REST facade endpoints: deferred; can be revisited if external client demand increases.
