# ADR-004: Event-driven processors for order progression

## Status
Accepted

## Date
2026-04-02

## Context
Order lifecycle progression spans multiple bounded services. `OrderProcessor` runs a background service that detects orders leaving grace period and publishes integration events (`GracePeriodConfirmedIntegrationEvent`) through the event bus. `PaymentProcessor` subscribes to stock-confirmed events (`OrderStatusChangedToStockConfirmedIntegrationEvent`), executes payment simulation logic, and publishes success/failure integration events. Both processors are connected through RabbitMQ event bus subscriptions rather than direct synchronous API coupling.

## Decision
Use event-driven processing between Ordering-adjacent workers (`OrderProcessor`, `PaymentProcessor`) and other services via integration events on the message bus.

## Consequences
- Pros: Loose coupling between services, independent scaling, and clearer domain boundaries.
- Pros: Failures in one processor do not synchronously block upstream request paths.
- Cons: Eventual consistency requires explicit monitoring, retries, and idempotency handling.
- Cons: End-to-end flow debugging is more distributed than synchronous request chains.

## Alternatives considered
- Synchronous HTTP orchestration between services: rejected due to tighter coupling and higher cascade-failure risk.
- In-process orchestration inside Ordering API: rejected because it mixes long-running concerns with request handling.
- Workflow engine introduction now: deferred; current event bus approach is sufficient for existing complexity.
